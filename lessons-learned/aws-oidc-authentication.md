# Lessons Learned: Troubleshooting GitHub Actions OIDC Authentication with AWS IAM

> **Author:** DevSecOps Team  
> **Topic:** Keyless AWS Authentication via GitHub Actions OIDC & IAM Role Trust Policies  
> **Target Audience:** DevOps Engineers, Security Engineers, Cloud Architects  

---

## Executive Summary

Migrating from long-lived AWS IAM access keys to OpenID Connect (OIDC) federated identity is a critical security upgrade for modern CI/CD pipelines. OIDC allows GitHub Actions workflows to request short-lived, auto-expiring AWS credentials without storing secrets in GitHub.

During implementation, we encountered and solved two major failure modes:
1. **The 4-minute hanging retry loop** caused by AWS STS Session Tagging (`sts:TagSession`).
2. **The `Not authorized to perform sts:AssumeRoleWithWebIdentity` (403 Access Denied)** caused by GitHub's **Immutable Subject Claims** (`@owner_id`/`@repo_id`).

This document provides a postmortem, technical root-cause analysis, and step-by-step resolution guide suitable for technical articles and team knowledge sharing.

---

## Problem #1: Workflow Stalling on "Assuming role with OIDC"

### Symptoms
The GitHub Actions workflow hung for **4 minutes and 38 seconds** at step `aws-actions/configure-aws-credentials@v4` with repetitive logs:
```text
Assuming role with OIDC
Assuming role with OIDC
Assuming role with OIDC...
Error: Job timed out.
```

### Root Cause
By default, `aws-actions/configure-aws-credentials` attempts to pass **Session Tags** (repository name, commit SHA, runner actor, workflow run ID) to AWS STS during role assumption.

When session tags are included in the request, AWS STS requires the IAM role's Trust Policy to permit both:
- `sts:AssumeRoleWithWebIdentity`
- `sts:TagSession`

If the IAM Role Trust Policy only lists `"Action": "sts:AssumeRoleWithWebIdentity"`, AWS STS rejects the tag session request. The AWS SDK inside the GitHub Action retries exponentially until the runner step times out.

### The Fix
Option A: Skip session tagging in the workflow:
```yaml
- name: Configure AWS Credentials via OIDC
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::916923735465:role/OIDC_SAAS
    aws-region: us-east-1
    audience: sts.amazonaws.com
    role-skip-session-tagging: true
```
Option B: Update the IAM Role Trust Policy `Action` to allow both actions:
```json
"Action": [
    "sts:AssumeRoleWithWebIdentity",
    "sts:TagSession"
]
```

## Problem #2: `Not authorized to perform sts:AssumeRoleWithWebIdentity` (403 Access Denied)

### Symptoms
After resolving the timeout, AWS STS immediately returned an Access Denied error:
```text
Error: Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

### The Breakthrough Discovery: GitHub Immutable Subject (`sub`) Claims
We added a JWT token claim inspection step to inspect the exact payload generated by GitHub Actions:

```json
{
  "iss": "https://token.actions.githubusercontent.com",
  "sub": "repo:si3mshady@46078321/rolex-price-api@1319412467:ref:refs/heads/feature/github-actions-oidc",
  "aud": "sts.amazonaws.com",
  "repository_owner": "si3mshady",
  "repository": "si3mshady/rolex-price-api"
}
```

### Root Cause
GitHub Actions OIDC tokens embed **Immutable Organization & Repository Numeric IDs**:
- `si3mshady` -> `@46078321` (Owner ID)
- `rolex-price-api` -> `@1319412467` (Repository ID)

Because the token sent `repo:si3mshady@46078321/rolex-price-api@1319412467:ref:refs/heads/...`, the standard trust policy condition `"repo:si3mshady/rolex-price-api:*"` **failed string matching** in AWS STS.

## Problem #3: AWS IAM Console "6-Character Wildcard Rule"

### Symptoms
When saving the updated trust policy in the AWS IAM Console, the validator threw an error:
```text
Overly permissive use of wildcard for the token.actions.githubusercontent.com:sub condition key. Use the wildcard preceded by 6 consecutive characters.
```

### Root Cause
AWS IAM Console enforces a security rule: wildcards (`*`) in `token.actions.githubusercontent.com:sub` conditions must be preceded by at least **6 literal characters**. Patterns containing short wildcard sequences like `:*:*` are blocked by AWS.

### The Solution
Patterns like `"repo:si3mshady@46078321/rolex-price-api@1319412467:*"` contain **50 literal characters** before the wildcard `*`, which completely satisfies AWS IAM Console validation.

## Verified Production Solution

### 1. Final AWS IAM Role Trust Policy
This Trust Policy supports both classic name-based claims and immutable ID-based claims while passing AWS Console validation:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Federated": "arn:aws:iam::916923735465:oidc-provider/token.actions.githubusercontent.com"
            },
            "Action": "sts:AssumeRoleWithWebIdentity",
            "Condition": {
                "StringEquals": {
                    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
                },
                "StringLike": {
                    "token.actions.githubusercontent.com:sub": [
                        "repo:si3mshady@46078321/rolex-price-api@1319412467:*",
                        "repo:si3mshady/rolex-price-api:*"
                    ]
                }
            }
        }
    ]
}
```

### 2. GitHub Actions Workflow Configuration
Located at `.github/workflows/verify-aws-oidc.yml`:

```yaml
name: Verify AWS OIDC Authentication

on:
  workflow_dispatch:
  push:
    branches:
      - 'feature/*'
      - 'develop'

permissions:
  id-token: write  # Required for GitHub OIDC JWT token generation
  contents: read   # Required for repository checkout

jobs:
  verify-oidc:
    name: Verify AWS OIDC Connection
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Configure AWS Credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::916923735465:role/OIDC_SAAS
          aws-region: us-east-1
          audience: sts.amazonaws.com
          role-skip-session-tagging: true

      - name: Print AWS Caller Identity
        run: |
          aws sts get-caller-identity
```

## Key Takeaways for DevOps Engineers

1. **Always Inspect the OIDC JWT Payload First**: When OIDC auth fails, decode the token payload (`$ACTIONS_ID_TOKEN_REQUEST_TOKEN`) to inspect the exact `sub` and `aud` strings sent by GitHub.
2. **Account for GitHub Immutable Claims**: Newer repositories include numeric `@owner_id` and `@repo_id` tags in the `sub` claim.
3. **Watch Out for Session Tagging (`sts:TagSession`)**: If your trust policy doesn't explicitly grant `sts:TagSession`, set `role-skip-session-tagging: true` to prevent SDK retry loops.
4. **Follow Least Privilege**: Maintain repository-scoped conditions (`repo:org@id/repo@id:*`) to prevent cross-repository role assumption.
